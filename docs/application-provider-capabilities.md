## Why discoverability ≠ application support (CLAUDE.md section 15)

Every ATS above except `lever` and `generic` also has a fully-supported (`FULL`/`PARTIAL`)
*discovery* connector in `app/providers/` — Ashby, Workable, SmartRecruiters, BambooHR, Breezy,
Recruitee, Comeet, Teamtailor all successfully find jobs. None of them were live-verified to
expose a legitimate, candidate-side, public application-question schema, so none of them claim
more than `UNSUPPORTED` on the *application* side. This is a deliberate, permanent separation
(`app.applications.provider.ApplicationProvider` vs. `app.providers.base.JobProvider`) — a
provider fully supported for discovery may be completely unsupported for application, and this
project never infers one from the other.

## Workday (CLAUDE.md sections 20, 57)

Workday remains tenant-specific by design — no universal hidden auto-apply system was built or
attempted. `GenericAssistOnlyProvider` covers it exactly like every other unsupported ATS:
apply-URL only, full package preparation, `NEEDS_USER_ACTION` for the candidate to complete the
tenant-specific flow (which typically requires an account) manually.

## Real submission policy applied to every provider (CLAUDE.md section 15)

`submission_supported=True` is set only when a provider has:

1. A documented, public, legitimate interface for candidate-side application automation, or
2. (For the mock fixture only) a deterministic, fully-tested in-process stand-in used
   exclusively to prove the executor's own mechanics.

No real ATS in this project meets bar (1) as of this phase. Where an interface requires
employer/private credentials, isn't meant for candidate automation, has unclear/restrictive
terms, or would require browser-automation circumvention to reach, the provider stays
`ASSIST_ONLY`/`UNSUPPORTED` — never faked as `AUTO`.

## Reconciliation recheck (`confirmation_recheck_supported`, Phase 9 addition)

A new, separate truthful flag from `submission_supported`: whether the provider exposes a
genuine way to re-check a *specific* application's status after the fact (used only by
`app.applications.reconcile_worker` — see `docs/application-reconciliation.md`). As of this
phase, only `mock_ats` sets it `True`; every real adapter honestly reports `False` since none of
these ATSes expose such an interface to candidates.

## Phase 10: a SEPARATE browser-assist matrix

This table describes the Phase 8 network-API-based `ApplicationProvider` adapters only. Phase 10
added real-browser assist (`app.applications.browser_assist`/`browser_runtime`), which is
**provider-agnostic by construction** — the same generic DOM-scan engine reaches Greenhouse,
Lever, and Ashby's real, live application forms (live-verified this phase — see
`docs/real-ats-validation.md`) with no per-provider code at all, including for `lever`, whose row
above correctly shows `UNSUPPORTED` for the *network-API* path. Its own separate, dated,
genuinely-observed capability table lives in `app.applications.browser_capability_matrix` /
`GET /applications/browser-capability-matrix` / `python -m app.applications.cli
browser-capability-matrix` — see `docs/browser-assist-sessions.md` and
`docs/phase10-real-ats-assist.md`. Discovery support, this table's application-provider support,
and the browser-assist table are three deliberately independent axes; none is ever inferred from
another.
